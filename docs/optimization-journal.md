## 2. 保留期查询：从全表扫描变为覆盖范围扫描

真实 SQL：`SELECT id FROM requests WHERE finished_at<:cutoff ORDER BY finished_at,id LIMIT 256`。

`v05-retention-index.json` 在 1,139,436 行历史数据及2,000条合成过期记录上，十次平均：忽略新索引 **2797.93 ms**，自动选索引 **0.83 ms**。before用IGNORE模拟同库缺索引；after没有FORCE。前后256个ID顺序哈希相同，实际执行由全表扫描/filesort变成索引扫描256条即停止。永久 `(finished_at,id)` 在0005迁移中。

候选建索引 3.79 秒；清理2,000条使用256条上限、9次短事务（包含最后0条），单批最长 176.25 ms。本机暖库，不承诺生产所有查询同等收益。旧0.4候选在此次实际完成，而非继续列“待实验”。

## 3. 写入成本：测量而非宣称索引免费

`v05-index-write-cost.json` 在专用测试库的随机独立表，复制同样其他索引，4轮无/有/有/无，每轮20,000行、每256行事务：

- 第1轮：无保留索引，5960.88行/秒，3.355秒。
- 第2轮：有保留索引，5744.69行/秒，3.481秒。
- 第3轮：有保留索引，5497.13行/秒，3.638秒。
- 第4轮：无保留索引，6036.16行/秒，3.313秒。

有/无轮次差异与本机波动重叠，不能得出固定百分比写损耗。实验只测INSERT，不覆盖全部终态UPDATE/长期碎片。索引有空间和维护成本；保留理由为明确的百万行清理查询及最终完整HTTP写入验收。第一轮脚本漏引保留字usage导致1064，修正后完整重跑，失败报告保留。临时表已删除，没有清空现有数据。

## 4. 状态统计：避免对成功行逐行回表

旧诊断 `GROUP BY status,error` 会读取大量error值；新版拆成使用已有应用/状态索引统计状态，以及只对稀少异常读取error。相同请求数据校验总数和异常分组相等。最终实测平均：旧 **10819.063 ms**，覆盖状态 **51.169 ms**，异常分组 **0.507 ms**。报告 `v05-query-diagnosis.json` 保留真实EXPLAIN ANALYZE。

旧查询曾超过正式驱动5秒预算，诊断专用连接改60秒以获得完整测量，服务仍3/5/5秒。该改写用于实验结果核验，不冒充 `/stats` 聚合API也已获得同样加速。`/stats` 仍有本应用与1—168小时范围，包含更多SUM/AVG字段；高频全量聚合需要独立业务需求和验证。

## 5. SQL 事务和连接

鉴权独立AUTOCOMMIT读取池，写入保留真实事务，不更改flush_log=1与sync_binlog=1。有界专用执行池、自然聚批、Redis pipeline减少往返；这些沿用既有正确实现，没有凭新版组合压测伪造单项提速比例。对账/清理RC、SKIP LOCKED及有界256条，新增真实四线程并发测试，锁定行跳过、其余仅删一次，活动/新记录保留。

SQL执行取消不能中止线程，槽位实际完成才返还；只重试MySQL明确回滚的1213死锁，连接断开/提交未知不重放。新增SQL指纹表只用于配置注册，不用于每次续约。

## 6. 实际发现的协议问题

Redis强杀实验第一轮发现停止响应任务后HTTP分块未完整结束。新增发送状态跟踪：失租/总超时尽力发送计入预算的SSE错误并结束more_body；0.25秒预算，断连时不再写。独立cleanup继续关闭上游并释放租约。复测10项通过，旧流无假DONE、恢复窗口503、上游active归零、再次200。

初次实验版注册表64字符与最终配置80字符不一致，0005规范为80；专用测试库的已应用中间版本单次对齐，新增80字符真实MySQL边界测试。最新空库迁移和回退/升级验证均通过。

## 7. 正式十万请求与带宽

最新无MQ代码：4进程、32闭环并发、SQL128 MiB、24连接预算、固定198字节无推理上游，100,000请求全部200：**416.15 QPS，p95 139.72 ms，p99 193.38 ms**，240.2964秒。包含预热的SQL记录100,096条均succeeded，12项恢复检查通过，核心源码SHA一致。不是模型推理QPS、公网峰值或生产负载均衡验收。旧32进程/1GiB/Streams的1,045.77成绩不用于新版简历。

- 65720字节实际响应正文（内容65536字节），8并发两轮：122.45 QPS / 64.381 Mbps / p95 90.55ms; 129.97 QPS / 68.332 Mbps / p95 86.74ms
- 1040184字节实际响应正文（内容1040000字节），8并发两轮：93.55 QPS / 778.477 Mbps / p95 97.2ms; 91.86 QPS / 764.396 Mbps / p95 100.05ms

正文带宽为字节×8/耗时，不包含HTTP/TCP/TLS，全部本机回环。长流16并发、每流200帧×4096字节、0.025秒请求节奏：12成功4途中取消，首帧p95 310.34ms，正文约12.94Mbps，上游active归零。实际节奏受事件循环与fixture断连检查影响，不是模型生成速度。慢消费者实际TCP实验及ASGI send超时在HTTP/单元验收。

## 8. 暂不分库分表

百万级实验历史总表仍可通过索引、短事务和保留期控制；固定小JSON瓶颈含HTTP及提交等待，不足以证明单库容量耗尽。没有长期每日千万行需求、备份窗口或持续I/O饱和证据，不增加分片复杂性。app_id为潜在路由边界，但当前没有实现分片。requests外键与唯一键限制使MySQL时间分区不能当免费开关。

## 补充：真实 `/stats` 接口，不能只优化实验核验 SQL

最终审查直接调用100,096条记录应用的statistics，正式5秒驱动预算超时。0006增加虚拟BIGINT派生列及统计覆盖索引，正式方法SUM派生值。旧表达式与新表达式三轮结果相同：旧平均 10388.40ms，新平均 97.40ms。EXPLAIN ANALYZE确认自动选择ix_app_statistics覆盖扫描；实际HTTP 171.34ms、200、100096条，服务驱动仍5秒。记录 reports/v05-statistics-index.json。

没有通过裁剪统计窗口或增加超时掩盖问题。派生值由数据库按JSON自动维护，不引入应用双写一致性。新索引确有维护/空间成本；独立20,000行ABBA：
- 第1轮：无统计索引，6164.46行/秒，3.244秒。
- 第2轮：有统计索引，5764.63行/秒，3.469秒。
- 第3轮：有统计索引，5729.69行/秒，3.491秒。
- 第4轮：无统计索引，5638.33行/秒，3.547秒。
这是INSERT成本，不代表长期UPDATE/碎片无成本。新列测试先误取accepted分组得到0，改为汇总所有状态并验证JSON更新后自动变化；并发清理测试误将空SKIP LOCKED批次视为全局清空，修正后在其他事务结束后继续有界清理，验证无重复和锁定/活动行保留。最终测试未减少功能断言。
